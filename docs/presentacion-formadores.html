Diseño del reto

Estructura mínima de cada enunciado

1

Cambio funcional

Una historia de usuario concreta, con entrada y salida clara. Debe ser implementable en 20–25 minutos de código.

2

Prueba obligatoria

Al menos 1 test que valide el comportamiento esperado. El andamiaje del test ya viene en el start — el participante lo hace pasar.

3

Criterio no funcional

Elige uno de los cuatro. Garantiza que el reto no sea "solo codear" y diferencia seniorities.

Criterios no funcionales

Calidad — diseño limpio, SOLID, cobertura
Performance — tiempo de respuesta, N+1
Operación — logs, health, métricas
Seguridad — validación input, datos sensibles

Diferenciación por seniority

JuniorReqs funcionales y tests básicos
Semi-seniorSOLID + tests significativos
SeniorDiseño desacoplado, criterio NF cubierto
ExpertoTrade-offs, mejoras, código mejor que lo encontrado

Seguimiento

Badges y métricas clave

🏅 ¿Qué es un badge?

Un badge no es un certificado ni un archivo — es un GitHub Issue cerrado con el label ✅ completado.

Sirve como registro público en el repo: filtras issues por ese label y ves exactamente quién completó qué sesión.
● ✅ [week-02] robinson completó la sesión
✅ completado week-02 abierto por robinson8406 · cerrado por formador

📋 Flujo paso a paso

  1. 1
    Participante abre PR desde week-XX/tu-alias hacia week-XX-start, asigna 1 reviewer
  2. 2
    Reviewer valida checklist de criterios-evaluacion.md y aprueba el PR
  3. 3
    Participante abre un Issue con título exacto: ✅ [week-XX] alias completó la sesión
  4. 4
    Formador verifica el PR aprobado, cierra el issue y aplica label completado → badge otorgado

% PRs aprobados · temas con más fallos en pipeline · sesiones con baja participación → ajustar el backlog.

⚖️ Reglas que no se negocian

Sin PR aprobado = sesión pendiente. No bloquea asistencia, sí el badge.
Sesiones autocontenidas: quien no asistió puede completar con week-XX-start + solución publicada.
Un reto único para todos. El nivel se evidencia en cómo se resuelve.
