Cada jueves

¿Qué pasa en la hora de sesión?

0–10'

Contexto + Demo

El formador explica qué vamos a mejorar y muestra el código inicial en vivo.

10–45'

🔥 Tu turno — Reto Intermedio

35 minutos de implementación real en el repo. Tú escribes el código desde tu rama personal.

45–55'

Validación

Ejecutamos tests. El pipeline tiene que quedar verde. Revisión rápida de 1-2 soluciones en vivo.

55–60'

Cierre

Se publica la solución de referencia. Puntos clave y dudas frecuentes.

Todo reto incluye:

1 cambio funcional — historia de usuario concreta
1 prueba — test que debes hacer pasar
1 criterio no funcional — calidad, performance, operación o seguridad
Estructura de ramas
week-XX-start → el andamiaje
week-XX/tu-alias → tu solución
week-XX-solution → referencia (min 55)
El reto intermedio único

Siempre incluye estas 3 partes

1
⚙️

Cambio funcional

Una historia de usuario real y concreta. Sabes qué tiene que hacer el código y qué resultado esperas.

"El sistema debe calcular el descuento de tipo LOYALTY para pedidos mayores a $100"
2
🧪

Prueba obligatoria

Al menos 1 test que valide tu implementación. El andamiaje ya está en el start — tú lo haces pasar.

El test ya existe y falla en rojo. Tu trabajo: hacerlo verde.
3
📐

Criterio no funcional

Cada semana se define uno de cuatro tipos. Esto es lo que eleva el reto más allá de "solo codear".

Calidad · Performance · Operación · Seguridad
El reto es el mismo para todos. Lo que cambia es la profundidad con que lo resuelves.
Flujo completo

Tu recorrido en cada sesión

1

Actualiza tu repo local

El lunes antes de la sesión el formador publica la rama start.

git fetch origin
2

Crea tu rama desde el start

Nunca trabajes directamente sobre main o week-XX-start.

git checkout week-XX-start
git checkout -b week-XX/tu-alias
3

Implementa, haz tests pasar

Escribe el código, ejecuta los tests localmente. Pipeline verde = listo.

./mvnw test
4

Abre tu PR y asigna reviewer

Push + PR hacia week-XX-start con 1 compañero como reviewer.

git push origin week-XX/tu-alias
Pipeline automático:
Al abrir el PR, Azure DevOps ejecuta mvn verify.
Verás ✅ o ❌ directamente en tu PR de GitHub.
5

PR aprobado → badge

Abre un issue con el título: ✅ [week-XX] alias completó la sesión

Reglas del PR

Usa el template en .github/PULL_REQUEST_TEMPLATE.md
Asigna exactamente 1 reviewer — un compañero
El reviewer valida el checklist de criterios-evaluacion.md
Sin PR aprobado = sesión pendiente (el badge no se otorga)
No bloquea asistencia ni acceso a la siguiente sesión
Convenciones de commit
feat:nueva funcionalidad test:añadir o modificar tests refactor:refactorización sin cambio de comportamiento fix:corrección de bug
Un reto · Todos los niveles

¿Qué se espera de cada seniority?

Junior

Implementa y verifica

  • Requerimientos funcionales cumplidos
  • Tests básicos pasando en verde
  • Código que compila y el pipeline no falla
Semi-senior

Diseña y valida

  • Aplica principios SOLID en la solución
  • Tests con casos de borde significativos
  • Separación de responsabilidades visible
Senior

Desacopla y opera

  • Diseño desacoplado y extensible
  • Tests robustos con mocks correctos
  • Criterio no funcional cubierto explícitamente
Experto

Mejora y propone

  • Identifica trade-offs y los documenta
  • Propone mejoras más allá del enunciado
  • El código queda mejor de como lo encontró

La filosofía clave

No hay ejercicios fáciles y difíciles.

Hay una solución mínima que cualquiera puede entregar, y una solución de calidad que demuestra madurez técnica real.

El senior no hace un problema más difícil — hace mejor el mismo problema.
